01Check your Claude plan

Claude Code needs a Pro, Max, Team or Enterprise plan, or a Claude Console account. The free plan does not include Claude Code. If you already pay for Claude, you are ready.

Do this before anything else

There is no point installing until the plan is sorted. The sign-in step at the end will simply refuse, and it is a confusing place to get stuck.

02Choose how you want to work

Three ways to run the same thing. You can change your mind later, and they share the same account, rules and history.

My recommendation

Use VS Code. You never have to write code in it — you are using it as a viewer with Claude attached. The reason it beats the others for this project is the diff view: you see exactly what Claude wants to change, in colour, and nothing happens until you approve it. That is the single best safety net for someone learning.

Desktop app

04Set up VS Code

VS Code is a free code editor from Microsoft. We are using it as a comfortable window onto your project with Claude attached to the side.

Step 1

Download and install VS Code from code.visualstudio.com. Accept all the defaults.

Step 2

Open VS Code and click the Extensions icon in the left bar — it looks like four small squares. Or press Command + Shift + X on Mac, Ctrl + Shift + X on Windows.

Step 3

Search for Claude Code and install the one published by Anthropic. There are imitations; check the publisher name.

Step 4

A small spark icon appears. Click it to open the Claude panel, then sign in when your browser opens.

Worth knowing

The extension includes Claude Code inside it. You do not need to install anything from step 3 as well. If the spark icon does not appear, press Command/Ctrl + Shift + P, type Developer: Reload Window and press Enter.

05Using VS Code day to day

You only need four things. Everything else is optional.

WhatHow

At the bottom of the prompt box is a mode selector. Keep it on the mode that asks permission before each edit while you are learning. Auto-accept is faster and much less forgiving.

06Make the project folder

Claude Code works inside one folder. That folder is "the project".

Step 1

Create the folder in your home folder — the one with your name on it, reached in Finder with Command + Shift + H. Name it flipgazine. Put it there and not in Documents: the scheduled job in section 19 looks for it at exactly that location.

Step 2

Put the deploy files in it: index.html, _worker.js, _headers, _redirects, sw.js, flipbook-ui.js, flipbook-core.js, flipbook-core.css, manifest.webmanifest, and the icons and og folders — the same files you upload to Cloudflare.

Step 3

Open it in VS Code with File → Open Folder.

Never move _worker.js into a functions folder

_worker.js sits at the root, beside index.html, and it is what gives every link its own preview title and description. Cloudflare's conventional location for this is a functions/ directory — and moving it there will silently break it, because the dashboard drag-and-drop deploy uploads a functions folder without ever compiling it, and reports success anyway. That mistake cost three deploys to find. It stays where it is unless you switch to deploying with Wrangler or Git.

The file itself almost never changes. What a page or a share says in a preview lives in the fg_page_meta and fg_shares tables, so new books and new share links need no deploy at all.

Remember what is not in this folder

This folder is only the shell. The six books, the home page, the reader and the CMS all live in the Supabase database, not on your computer. That is why step 8 matters, and why "edit the book" almost never means "edit a file here".

Step 1

Drop the CLAUDE.md file into the flipgazine folder, alongside index.html.

Step 2

Keeping it useful

08Connect Supabase

This gives Claude Code the same database reach it has in our chats. Without it Claude can see your shell files but none of your books.

In VS Code or the desktop app: open the plugin and connector manager from the panel, choose to add a connector, and give it this address:

https://mcp.supabase.com/mcp

In the terminal: run this before starting a session:

claude mcp add --transport http supabase https://mcp.supabase.com/mcp

Then start Claude Code and type:

/mcp

You will be sent to your browser to sign in to Supabase. Approve it once and it stays connected.

The project reference

flipgazine lives in project sjpvhgxacsiorrtijqua. That database is shared with unrelated projects, so tell Claude to stay in the flipgazine tables. The rules file says this too, but it is worth knowing yourself.

10Set up your team of subagents

A subagent is a specialist Claude can hand a job to. It works in its own separate context, with its own instructions and its own limited set of tools, then reports back. Two reasons this matters here: a read-only subagent cannot damage anything, and side quests stay out of your main conversation instead of clogging it.

The easy way to make one is to type:

/agents

It walks you through it and writes the file for you. Subagents are plain text files in a .claude/agents/ folder inside your project. Here are three worth having for flipgazine — you can also just paste each block to Claude and ask it to create the file.

1. The surgeon — makes database edits carefully

--- name: fg-surgeon description: Makes careful edits to flipgazine pages and books in the Supabase site_files table. Use for any change to a book, the home page, the reader or the CMS. --- You edit flipgazine content that lives in the Supabase site_files table. Before every edit: - Confirm the anchor string appears exactly once. Postgres replace() hits every occurrence. - Show the SQL and wait for approval before running it. After every edit: - Prove it landed: query that the new string is present and the old string is gone, and report the row length. Never delete a row without first checking what serves that path. Never touch tables belonging to the other projects that share this database.

2. The inspector — read-only, cannot break anything

--- name: fg-inspector description: Read-only investigator for flipgazine. Use to find where something lives, audit a page, or check a change went in correctly. Never writes. --- You investigate the flipgazine project and report findings. You never write, update or delete anything, in files or in the database. Useful checks: - Which site_files row actually serves a given path. - Whether an anchor string is unique before an edit is attempted. - Whether an edit landed: new string present, old string absent. - Whether an anonymous visitor can read a row, using a role anon check. Report what you found plainly, including anything that looks wrong but was not asked about.

3. The designer — visual work in the flipgazine style

--- name: fg-designer description: Visual and front-end work on flipgazine - layout, typography, colour, WebGL backgrounds, book covers. Use whenever a change is about how something looks. --- You handle the look of flipgazine. Use the front-end design skill. House rules: - Palette and type come from the home page tokens. Do not invent new colours; use the existing custom properties so pages follow the daylight theme. - Each book keeps its own accent. Do not standardise them. - Some things look like bugs but are deliberate: reduced motion is switched off site-wide, and the Lobby Lounge cover emboss is stronger than the other five. - You cannot see the result. Validate the code, then say plainly that the pixels are unverified and ask for a look.

How to use them

Mostly you do not have to. Claude reads each description and hands work over automatically. You can also ask directly: "use fg-inspector to check whether that change landed". Restart the session after adding a new agent file so it gets picked up.

11Your first session

Read CLAUDE.md, then list the six flipgazine books in site_files with their sizes. Do not change anything.

If that comes back right, the whole chain works: Claude read your rules and reached your database. Now a real but small change:

In the Sip & Co. book, change the cover tagline to "Find your Co. in Langsuan". Show me the SQL first and check the anchor is unique before running it.

Ask for the plan before the work. One extra message prevents most bad days — and in VS Code you get the diff as a second checkpoint.

13Golden rules for flipgazine

These come from mistakes already made on this project. They are in CLAUDE.md too, but knowing them yourself lets you catch a wrong turn early.

  • Editing a book is a database edit, not a file edit. If Claude starts hunting for book HTML in your folder, stop it and point it at site_files.
  • Redeploy is only for the shell. index.html, sw.js, _redirects, _headers, flipbook-ui.js and icons. Everything else is live the moment the database changes.
  • Never delete a row without checking what serves it. This once took the books offline.
  • The database is shared. If Claude mentions tables like shops, trips or book_chapters, it has wandered into another project. Redirect it.
  • Claude cannot see the result. It can validate code and maths but not pixels. You are the eyes — always load the page and report back.
  • Ask it to prove the change landed. The proof is a query showing the new text present and the old text gone.

16Running two jobs at once

Sooner or later you will want Claude working on two things at the same time — say, restyling a book while a second job fixes the CMS. Opening two sessions on the same folder is the obvious move and the wrong one: both are editing the same files, so they overwrite each other and each ends up confused about what the file contains.

The fix is a worktree: a second copy of your project folder, on its own branch, sharing the same history. Each session gets its own files and cannot disturb the other. Claude Code creates and cleans them up for you.

Read this before you use it here

Worktrees isolate files. They do not isolate the database — and almost everything in flipgazine lives in the database. Two sessions in two worktrees are still writing to the same site_files rows, and the second one to save wins. Worktrees make parallel work safe on the shell files; they do nothing about collisions on a book. See the rule at the end of this section.

First, make the folder a git repository

Worktrees need git. If you have never run git in your flipgazine folder, do this once. In VS Code open the terminal panel with Terminal → New Terminal, then paste:

git init git add . git commit -m "flipgazine shell"

You do not need GitHub or any remote for this to work. Then add one line to a file called .gitignore so the worktree folders do not clutter your project:

.claude/worktrees/

Starting a session in a worktree

Give it a short name describing the job:

claude --worktree anju-restyle

That creates an isolated copy at .claude/worktrees/anju-restyle/ on a new branch called worktree-anju-restyle, and starts Claude inside it. Open a second terminal and run the same command with a different name for your second job:

claude --worktree cms-fix

The short form is -w. If you leave the name out, Claude invents one such as bright-running-fox.

Two easier routes

In the desktop app, every new session gets its own worktree automatically — nothing to type. And in any session you can simply say "work in a worktree" and Claude will move itself into one, which is useful when you realise mid-job that you want isolation.

The first time you use it you may be asked to trust the folder. If --worktree exits with a trust error, run claude once in the folder normally, accept the prompt, then try again.

Finishing up

Closing the session does not automatically throw away your work.

SituationWhat happens
Nothing was changedThe worktree and its branch are removed automatically.
There are changesClaude asks whether to keep or remove it. Keep preserves the folder and branch so you can come back; remove deletes the work with it.

To see what exists and tidy up by hand:

git worktree list
git worktree remove .claude/worktrees/anju-restyle

Giving a subagent its own worktree

Subagents can be isolated the same way, which matters if one is editing many files at once. Ask Claude to "use worktrees for your agents", or make it permanent for one agent by adding a single line to its frontmatter:

--- name: fg-designer description: Visual and front-end work on flipgazine. isolation: worktree ---

Claude removes those temporary worktrees itself once the agent finishes without leaving changes behind.

The rule for this project

  • Split parallel jobs by path, not just by worktree. One session on the ANJU book, another on the CMS — fine. Two sessions on the same book — the worktree will not save you, because the collision happens in the database.
  • Two or three at once is plenty. Beyond that you cannot review the output properly, and every session is drawing on the same usage allowance.
  • Worktrees earn their keep on the shell files — index.html, sw.js, flipbook-ui.js — and for trying an experiment without disturbing your main folder. For ordinary book edits, a single session is simpler and just as fast.

17Two Claude accounts on one Mac

If you have two paid Claude accounts — say a personal one and a work one — you can run both side by side on the same Mac, each in its own window, without logging out. Two accounts means two separate usage allowances, so a long job on one does not slow the other down.

Two honest warnings first

Each account needs its own paid plan. This is for people who genuinely have two, not a way to dodge usage limits by opening extra accounts — that risks the accounts themselves. If you just want more headroom, upgrade the plan you have.

Also, the setting below (CLAUDE_CONFIG_DIR) works and is what most people use, but it is not in Anthropic's official documentation. It could change without warning. If it ever stops working, use the supported fallbacks at the end of this section.

What we are actually doing

Claude Code keeps everything that makes an account yours — the login, settings, history, installed skills — in one folder on your Mac, normally called ~/.claude. If you point it at a different folder, you get a second, completely separate Claude Code. Same program, different identity.

So the whole job is: make a second folder, create a shortcut that uses it, and log in once. Five minutes, done permanently.

First: a two-minute terminal primer

Everything below is typed into the Terminal. If you have never used it, read this bit — it removes most of the fear.

  • Opening it. Press Command + Space, type Terminal, press Enter. If VS Code is already open you can instead use Terminal → New Terminal from its menu — it is the same thing in a panel at the bottom.
  • What you see. A line of text ending in a % sign. That is the prompt. It is simply waiting for you.
  • How to run a command. Copy it with the button on this page, click into the Terminal window, press Command + V to paste, then press Enter. Nothing runs until you press Enter.
  • Silence is success. Most of these commands print nothing at all when they work. An empty line and a fresh prompt means it worked. You only need to worry if you see the word error or not found.
  • The squiggle. ~ is shorthand for your home folder. A name starting with a dot, like .claude, is a hidden folder — Finder does not show it by default. That is normal, not a mistake.
  • You cannot break anything with the commands in this section. The worst case is a shortcut that does not work, and the last step shows you how to undo it.

Step 1 — check which shell your Mac uses

This decides which settings file we write to. Paste this and press Enter:

echo $SHELL

What you should see: /bin/zsh. That is the normal answer on any recent Mac, and the rest of this section assumes it.

If it said /bin/bash instead

You are on an older setup. Everything still works — just replace ~/.zshrc with ~/.bash_profile everywhere below.

Step 2 — make the folder for the second account

mkdir -p ~/.claude-second

What you should see: nothing. The prompt returns and that is correct. You have just created an empty hidden folder that will hold the second account.

Step 3 — create the two shortcuts

An alias is a nickname for a longer command. We are adding two nicknames — claude1 and claude2 — to a settings file your Terminal reads every time it opens, so they exist from now on.

echo "alias claude1='claude'" >> ~/.zshrc echo "alias claude2='CLAUDE_CONFIG_DIR=~/.claude-second claude'" >> ~/.zshrc

What you should see: nothing again. Those two lines added themselves to the end of the settings file. The >> means "add to the end of" — it does not overwrite what is already there.

Now tell the Terminal to re-read that file so the shortcuts work immediately, instead of having to close and reopen the window:

source ~/.zshrc

Step 4 — check the shortcuts exist

This one does print something, so it is a good confidence check:

alias | grep claude

What you should see: two lines, one for claude1 and one for claude2. If you see nothing, the shortcuts did not load — close the Terminal window completely, open a new one, and run this again.

Step 5 — sign in to the second account

Step 5a

Start the second Claude Code:

claude2
Step 5b

Because this folder is brand new, it behaves like a first-ever install: it will ask you to sign in and open your browser.

Step 5c

Sign in with your other account — not the one you normally use. This is the only moment where it matters which one you pick.

Step 5d

Return to the Terminal. You are now in a session on the second account. Type /exit to leave when you are done.

It may also ask whether you trust the folder you are in. Say yes — it is your own project folder.

Step 6 — running both at once

Step 6a

In your current Terminal window, type claude1 and press Enter. That is your usual account.

Step 6b

Open a second window with Command + N, or a second tab with Command + T.

Step 6c

In the new one, type claude2. Both are now running, each on its own account, neither aware of the other.

Label them before you get confused

Two identical windows is the easiest way to lose track. With a window selected, use Shell → Rename Tab from the Terminal menu and call them claude1 and claude2. Do it now rather than later.

From here on the routine is simply: open Terminal, type claude1 or claude2. Nothing to set up again.

Combining with worktrees

How to undo all of this

Nothing here is permanent. To remove the second account from your Mac, open the settings file:

open -e ~/.zshrc

That opens it in TextEdit. Delete the two alias claude1 and alias claude2 lines, save, and close. Then, if you also want to delete the second account's local data:

rm -rf ~/.claude-second

Be careful with that last one

rm -rf deletes permanently, with no trip to the Trash. Make sure the line reads exactly ~/.claude-second and not ~/.claude — the second one would delete your main account's settings. Your Claude account itself is untouched either way; this is only local data.

The rule, again

Everything from the previous section still applies, and more sharply. Two accounts do not give you two databases. Both are writing to the same site_files rows in the same Supabase project. Split the work by path — one account on a book, the other on the CMS or the shell — and never point both at the same page.

If the shortcut stops working

  • Switch instead of running both. Inside a session, /logout then /login moves you to the other account. Supported, but one at a time.
  • Use a second macOS user account. System Settings → Users & Groups, add a user, then switch with fast user switching. Heavier, but completely supported and fully isolated.

18The same two accounts on a second machine

Nothing stops you using the same accounts on a laptop as well as the Mac — a Claude subscription belongs to you, not to a computer, and signing in on several devices is expected. What surprises people is how much of your setup does not come with you.

What travels, and what does not

Travels by itselfMust be redone on each machine
Your accounts and plans — just sign in
The whole flipgazine site — it lives in Supabase, not on any computer
Claude chat conversations, projects and preferences sync across devices		 The Supabase connection (/mcp)
Skills and plugins (/plugin)
The sign-in for each account
Session history — stays on the machine that made it

Why the right-hand column exists

Claude Code keeps all of that in a folder on the machine itself, and there is currently no built-in way to sync it between computers. It is a frequently requested feature that does not exist yet. Budget about five minutes per machine, per account. Do not go looking for a sync setting — there isn't one.

The good news for this project is the first row. Because the books, the home page, the reader and the CMS all live in Supabase, your second machine does not need to carry the site at all. Connect it to the database and you are working on exactly the same content.

Step 1 — get the project folder onto the second machine

You only need this folder for the shell files, CLAUDE.md and your subagents. The tidy way is a private repository, which also keeps both machines in step from then on.

On the Mac, once:

git remote add origin https://github.com/YOURNAME/flipgazine.git git push -u origin main

On the second machine:

git clone https://github.com/YOURNAME/flipgazine.git

After that, git pull before you start work and git push when you finish keeps CLAUDE.md and your agents identical on both.

Do not put this folder in iCloud Drive or Dropbox

File-sync services corrupt git repositories — they copy the internal git files mid-write, and worktrees make it worse. If you would rather not use GitHub, copy the folder across manually instead and accept that you must re-copy CLAUDE.md whenever it changes.

Step 2 — install and sign in

Step 1

Install VS Code and the Claude Code extension exactly as in section 4, or the desktop app from section 3.

Step 2

Open the cloned flipgazine folder and sign in with your first account.

Step 3

Connect Supabase again — section 8. This is per machine and per account, so on a two-account machine you do it twice.

Step 4

Reinstall the skills you use — section 9. Type /context to confirm CLAUDE.md is loading, and you are running.

Step 3 — add the second account

If the second machine is a Mac or Linux, repeat section 17 exactly: make the folder, add the two aliases, run claude2 and sign in.

mkdir -p ~/.claude-second echo "alias claude2='CLAUDE_CONFIG_DIR=~/.claude-second claude'" >> ~/.zshrc source ~/.zshrc

If it is Windows, the idea is the same but the shortcut goes in your PowerShell profile. Paste this into PowerShell:

New-Item -ItemType Directory -Force -Path "$HOME\.claude-second" Add-Content -Path $PROFILE -Value 'function claude2 { $env:CLAUDE_CONFIG_DIR="$HOME\.claude-second"; claude @args }' . $PROFILE

Then open a new PowerShell window and run claude2 to sign in with the second account.

Keeping skills in step without a sync feature

Since there is no built-in sync, pick one of these and stick to it.

  • Simplest, recommended: install only the two or three skills you actually use, and reinstall them on each machine. Five minutes, no moving parts.
  • If a skill becomes essential to the project: keep it in the repository under .claude/skills/ instead of the account folder. Then it travels with git pull like CLAUDE.md does, and both accounts on both machines get it.
  • Avoid elaborate symlink-and-cloud-drive schemes. They are a known source of stale and half-copied files, and you do not need them for a project this size.

The rule, one last time

Two machines with two accounts each is up to four sessions writing to one database, and Supabase will not stop them colliding. The discipline is unchanged and matters more the more places you work from:

  • One page, one session. Split by path — never two sessions on the same book, whatever machine they are on.
  • Pull before you start, push when you stop. Otherwise the two machines drift apart on CLAUDE.md and your agents.
  • If something is overwritten, every write is snapshotted in site_files_versions. Ask Claude to restore the previous version of that path.

20Running Claude Code alongside Codex

Some jobs go faster with a second opinion from a different model. Codex is OpenAI's coding agent — it lives inside VS Code the same way Claude Code does, and both can be open on the same Mac without either one knowing the other exists. This section assumes you have already read Running two jobs at once: everything below builds on worktrees, it does not replace them.

Install Codex in VS Code

No terminal needed for any of this.

  1. Open the Extensions panel — the four-square icon on the left edge of VS Code, or Cmd+Shift+X.
  2. Search for Codex. Install the one published by OpenAI — it may list itself as "ChatGPT."
  3. A new Codex icon appears in the activity bar. Click it, then click Sign in with ChatGPT.
  4. Your browser opens to log in. You need a ChatGPT Plus, Pro, Business, or Enterprise plan — the free tier does not include Codex, and no API key is needed.

Signed in, the Codex panel works like a second Claude panel: a chat box that reads your open files and edits them directly, with its own local-versus-cloud toggle.

Give both tools the same rules

Claude Code reads CLAUDE.md. Codex reads a different file, AGENTS.md. Neither reads the other's automatically — left alone, the two will drift, and Codex will quietly miss every flipgazine-specific rule you have taught Claude.

The fix is a one-line import, not two files kept in sync by hand. Rename your existing CLAUDE.md to AGENTS.md — right-click it in the file explorer and choose Rename — then create a new CLAUDE.md containing just this:

@AGENTS.md ## Claude-specific (anything only Claude Code should follow goes here)

Claude Code expands that @AGENTS.md line at the start of every session, so it ends up reading the exact same rules Codex does, plus anything Claude-only underneath. AGENTS.md becomes the one real file; CLAUDE.md is a two-line wrapper pointing at it.

If you would rather not rename anything yourself

Ask Claude Code, in a normal chat message, to "create an AGENTS.md file next to CLAUDE.md with the same content, and turn CLAUDE.md into a one-line @AGENTS.md import." It is a file edit, not a terminal command, so it can do the whole thing for you.

Give Codex its own worktree

The rule from section 16 holds exactly the same way here: never point two agents at the same files at the same time. VS Code can create the worktree itself — no terminal required.

  1. Open the Source Control panel — the branch icon on the left edge.
  2. Find your repository, click the … menu beside it, then choose Worktrees → Create Worktree.
  3. Give it a short, descriptive name — the same naming habit from section 16 works here too.
  4. Choose Open Worktree in New Window. A second VS Code window opens on the new folder.
  5. In that window, open the Codex panel and start there. Claude Code keeps running in the original window, on the original folder, untouched.

The same database warning as section 16

A worktree isolates files on disk. It does not isolate flipgazine_moodboards, site_files, or any other Supabase table — both agents are still one Supabase project away from writing to the same row. Give Claude Code and Codex different books or different paths, exactly as you would two Claude sessions. Point them at the same book and the second save silently wins, worktree or not.

What VS Code is actually doing

Worth being exact about this, since it decides how carefully you need to work: VS Code does not coordinate the two tools. There is no lock, no queue, no handshake between Claude Code and Codex. What VS Code does is watch files on disk and reload a tab when the file underneath it changes.

  • Tab has no unsaved changes: VS Code reloads it silently the moment the other agent writes to it. This is the part that makes the two tools feel connected.
  • Tab has unsaved changes: VS Code stops and asks you to keep yours or take the version on disk. Nothing is lost silently, but nothing merges either — you are picking one side.
  • Both agents write to the same file at nearly the same moment: whichever save reaches disk second wins, in full, with no warning shown. This is the actual reason for separate worktrees — not a nicety, the only thing preventing this.

Splitting the work

Model rankings age quickly and both tools change every few months, so a rule like "Claude plans, Codex executes" will be wrong within a year. A split that holds up regardless of which model happens to be ahead: own by worktree, not by task type.

  • One agent, one worktree, one job, start to finish. Whichever tool starts a book restyle finishes it — don't hand a half-done job to the other mid-way, since neither has seen the other's uncommitted changes.
  • Review is the one thing worth crossing tools for. Once Claude Code commits a change in its worktree, open that same worktree in Codex (or the reverse) and have it read the diff before you merge to main. A different model reading your model's own output catches things a self-review misses.
  • The commit is the real handoff. Not a chat message, not a shared folder — the commit. If it isn't committed, the next agent can't see it and has no way to know to look.

Two Codex accounts in one VS Code window

The Codex extension only holds one signed-in account at a time, and OpenAI has an open, unresolved request for this exact feature. In the meantime, a small third-party extension handles the swap for you — no terminal, though it is switching between accounts, not running two at once. This example uses Codex Switch, which is the clearest-documented of the few that exist.

  1. Open Extensions (Cmd+Shift+X), search Codex Switch, and install the one published by WoozyMasta. Check the publisher name before installing — this is not an OpenAI extension, just one that manages OpenAI's own auth file.
  2. Sign into your first Codex account the normal way, as in the previous section, if you have not already.
  3. Open the Command Palette (Cmd+Shift+P) and run Codex Switch: Prepare for New Login. This saves your current account as a named profile and clears the active session so the login screen reappears. Use this, not a plain logout — logging out directly can invalidate that account's token, which means signing in from scratch again later instead of switching back to it.
  4. Click Sign in with ChatGPT and log into the second account. Codex Switch saves it as a second profile automatically.
  5. From then on, the status bar at the bottom of VS Code shows whichever profile is active. Click it to switch, or cycle through saved profiles — configurable in the extension's settings.

This swaps accounts, it does not run two

Only one account is signed in at any moment, in this window. If you genuinely need both accounts doing work at the same time, that needs two separate windows, each launched with its own CODEX_HOME folder — the same shape as the claude2 shortcut trick in section 17, just for Codex. Ask Claude Code to set that up for you if you need it; it is a one-time, five-minute job.

Writing a handoff before you switch

Codex does not carry the conversation across that reload — whatever it was reasoning through when you switch accounts is gone, not paused. A short file fixes this more reliably than memory would anyway, because it is something you can also read.

Before switching, ask for one. If you are working in a worktree, say so, so the file stays with that job rather than landing in the project root where a second job would overwrite it:

Before I switch accounts, write a handoff to handoff.md in this worktree. Include: what you're working on right now, what you've already tried and ruled out, what to do next, and anything you're waiting on me to decide. Keep it short enough to read in under a minute.

Wait for it to confirm the file is written, then switch. When you come back to that job — same account or the other one — open that same worktree and start with this:

Read handoff.md in this worktree before doing anything else, then pick up where it left off.

Why intent, not a list of changes

Every save is already snapshotted in site_files_versions, so Codex can always re-read what a file currently contains — that part does not need writing down. What a handoff needs to capture is the part that vanishes with the reload: why a decision was made, what was tried and rejected, and what you were about to ask it to do next.

The companion documents

CLAUDE.md in your project folder is the technical version of this manual, written for Claude rather than for you. /FLIPGAZINE_HANDOFF.md in the database holds the full architecture notes. Official Claude Code documentation is at code.claude.com/docs.

21Building a new interface page without drift

flipgazine now has one persistent interface system. The shared header, session gate, clock, navigation router, fonts, palette preload, WebGL atmosphere, glyph field, theme and transition modules are started centrally. A new page supplies only its own content, styles and—when it has behaviour—a lifecycle controller.

Do not start from an old page by deleting pieces until it looks right. Start from the small contract below. That keeps navigation seamless and lets the page be added or edited in Supabase without redeploying the Cloudflare shell.

Check CI before inventing or copying interface values. It is the living UX/UI reference for Flipgazine. Shared implementation should follow it; when CI and the product disagree, stop and resolve the drift instead of treating whichever file you opened first as canonical.

The current page skeleton

Every interface page needs exactly one shared-head marker, at least one data-fg-page-style style block, one WebGL canvas, one glyph host, one shared-header marker and one page payload. This is the interactive form:

<!doctype html> <html lang="en" data-theme="dark" style="background:#0D1110"> <head> <meta charset="UTF-8"> <meta name="viewport" content="width=device-width,initial-scale=1"> <title>Page title · flipgazine</title> <!--FG_HEAD--> <style data-fg-page-style> /* Arrival fade. Stays inline, and must: it has to be parsed before the first paint, and fg-motion.js is fetched after the page has already rendered -- applying an opacity animation at that point flashes the content out and back. The overlay, its stacking, the click interception and the timing all live in the module; only these two lines cannot. */ @keyframes fgEnter{from{opacity:0}to{opacity:1}} body > main,body > #app,body > .wrap,#glCanvas,#bgLetters,#glyphs{animation:fgEnter 1.06s var(--ease-soft,cubic-bezier(.4,0,.2,1)) backwards} /* Page-specific styles begin here. */ </style> </head> <body data-fg-persist="interactive-v1"> <canvas id="glCanvas" aria-hidden="true"></canvas> <div class="bg-letters" id="bgLetters" aria-hidden="true"></div> <!--FG_HEADER--> <main id="main" data-fg-page data-fg-controller="/fg-page-example.js"> <!-- This page's content only. --> </main> </body> </html>

Only the arrival block stays page-local

The shared-head marker supplies Poppins and Noto Sans Thai, common tokens, [hidden], the fixed gradient, PWA metadata and the synchronous palette restore before first paint. Do not paste font links, a palette-preload script, theme-colour metadata or shared background rules into the page. The arrival block above is the one deliberate exception and must remain byte-for-byte identical on every interface page.

Choose the right lifecycle

Page typeBody and main contractUse it when
Staticdata-fg-persist="static-v1" on <body>; data-fg-page on <main>; no controller attribute.The page has no listeners, observers, timers, async rendering or page-owned global state. Privacy and Terms are the examples.
Interactivedata-fg-persist="interactive-v1" on <body>; data-fg-page and one data-fg-controller on <main>.Anything clickable, live, authenticated, database-backed or asynchronously rendered.

Never label an interactive page static-v1 just to make its transition persistent. Missing cleanup accumulates old handlers and timers after each visit. Without a valid contract the router deliberately falls back to a normal full-document load.

The controller contract

An interactive page keeps its JavaScript in a separate /fg-page-name.js row. It registers one controller under the exact same path used by data-fg-controller. mount(main) starts page behaviour; unmount() removes every resource that page owns.

(function(){ var PATH="/fg-page-example.js"; var registry=window.FGPageControllers||{}; var state=null; window.FGPageControllers=registry; function unmount(){ if(!state) return; state.abort.abort(); if(state.observer) state.observer.disconnect(); if(state.timer) clearTimeout(state.timer); state=null; } function mount(main){ if(state&&state.main===main) return; unmount(); var current={main:main,abort:new AbortController(),observer:null,timer:0}; state=current; main.addEventListener("click",function(e){ if(state!==current) return; /* Page behaviour. */ },{signal:current.abort.signal}); } registry[PATH]={mount:mount,unmount:unmount}; })();

Clean up document/window listeners, observers, intervals, timeouts, subscriptions, realtime channels, object URLs and temporary DOM. Abort or generation-guard asynchronous work so a page that has already unmounted cannot render or write later.

What the centralized interface already owns

The shared header creates the readiness promise immediately, completes the session/invite check, starts Dev Nav once and exposes FGInterfaceReady. It also loads motion, theme, glyph and atmosphere modules in canonical order. The navigation router waits for readiness before committing a compatible page swap.

  • Do not call FGModules.load(...) from the page.
  • Do not load fg-devnav.js, fg-prefetch.js, fg-motion.js, fg-theme.js, fg-glyph.js, fg-atmos.js or fg-runtime.js yourself.
  • Do not copy header markup/CSS, F_PATHS, the clock bootstrap, module loader, WebGL shaders, glyph generation, Dev Nav or an element named fgFade.
  • Do not add page-local .rule / .fg-progress-rule styling or a second #ruleFill. The progress component belongs to /fg-header.html; /fg-motion.js owns its scroll logic.
  • Do not create a second animation loop. Shared atmosphere time, glyph seed, session and header nodes are intentionally preserved across page navigation.

A footer logo needs only an empty <svg id="footerLogoMark" viewBox="0 0 646 676" aria-hidden="true"></svg>. The shared brand renderer fills it. The same header fragment owns the canonical .fg-progress-rule markup and CSS, so every interface page gets the same 2px / glow / 120ms progress treatment without a local copy.

Footer section rail / chip contract

Persistent interface pages that use a bottom section rail must follow the same component contract as Voice. This rule is for section-navigation chips only—not admin tab bars, pagination, book controls, toasts or unrelated fixed actions.

  • Use .bottom-nav for the rail, .nav-chip for every chip and .on for the active section. A page-specific action may add one semantic class such as .act or .nav-action, but it must inherit the same base geometry.
  • The rail is fixed to left/right/bottom 0 at z-index:40, horizontally scrollable, safe-centred, background:var(--glass), top border var(--glass-brd), and blur(18px) saturate(1.3). Do not invent a second footer surface.
  • Desktop chips are 30px high with 15px radius, 0 14px padding, 10.5px uppercase type, .1em tracking and weight 600. Active text and border use var(--accent).
  • At 639.98px and below, the rail uses a 7px gap and 8px 20px 10px padding plus the bottom safe area; chips use 10px type, 0 12px padding and .08em tracking.
  • Reserve roughly 62px + safe-area-inset-bottom below page content so the last section never sits under the rail.
.bottom-nav{ position:fixed;left:0;right:0;bottom:0;z-index:40; display:flex;gap:8px;align-items:center;justify-content:safe center; overflow-x:auto;overscroll-behavior-x:contain; scrollbar-width:none;-webkit-overflow-scrolling:touch; background:var(--glass);border-top:1px solid var(--glass-brd); padding-block:10px; padding-bottom:calc(10px + env(safe-area-inset-bottom,0px)); -webkit-backdrop-filter:blur(18px) saturate(1.3); backdrop-filter:blur(18px) saturate(1.3); } .nav-chip{ flex:0 0 auto;white-space:nowrap;text-decoration:none; height:30px;min-height:30px;border-radius:15px;padding:0 14px; font-size:10.5px;letter-spacing:.1em;text-transform:uppercase;font-weight:600; color:var(--muted);background:var(--glass);border:1px solid var(--glass-brd); display:inline-flex;align-items:center;justify-content:center; } .nav-chip.on{color:var(--accent);border-color:var(--accent);} @media(max-width:639.98px){ .bottom-nav{gap:7px;padding:8px 20px 10px; padding-bottom:calc(10px + env(safe-area-inset-bottom,0px));} .nav-chip{font-size:10px;padding:0 12px;letter-spacing:.08em;} }

Footer rail behaviour and lifecycle

  • A tap must mark the selected chip .on immediately, then smooth-scroll to its section. Do not wait for scrollspy before showing feedback.
  • Hold the tapped chip active during the smooth-scroll handoff (about 1.2s in the current controllers), then let scrollspy resume. Keep the active chip revealed/centred in the horizontal rail and update the hash without a full navigation.
  • Every rail listener, RAF and timer belongs to the page controller and must be cleaned up in unmount().
  • Never solve a footer paint bug with giant z-index values, translate3d, will-change, contain:paint, forced opacity or an opaque loading guard. The canonical rail stays at z-index 40.
  • If Android Chrome composites a fixed glass rail badly because it lives inside the canonical fgEnter-animated <main>, an interactive-v1 controller may portal that rail to document.body on mount and restore/remove it on unmount. Keep the source markup inside the one page payload so fg-nav.js can parse and own it. Voice is the proven reference.
  • Do not leave an invisible full-screen fixed element with backdrop-filter mounted behind the rail. Closed overlays must leave the render/compositor path until they are actually opened.

Database workflow—no shell redeploy

  1. Create the page row in site_files. For an interactive page, create its controller row too.
  2. Snapshot an existing row before a substantial edit. Prove every replacement anchor appears once.
  3. Run node --check on the controller and every executable script extracted from the page.
  4. Stage a large controller or replacement block in a temporary row and compare its MD5 before publishing.
  5. Confirm the page row is readable as anon, then test direct load and continuous navigation at desktop and mobile sizes.

Adding or editing a database-backed page does not redeploy Cloudflare. Redeploy only when changing the shell itself: index.html, service worker, redirects, headers, worker, manifest, icons or shared static flipbook files.

The corrected page audit

Replace the path in the last line. For an interactive page the structural checks should be 1; forbidden_local_copies and local_progress_copy must be 0. For a static page, controller must also be 0. This SQL has been executed against the live Home row.

with page as ( select content from public.site_files where path='/your-new-page.html' ) select (select count(*) from regexp_matches(content,'<!--FG_HEAD-->','g')) as head_marker, (select count(*) from regexp_matches(content,'<!--FG_HEADER-->','g')) as header_marker, (select count(*) from regexp_matches(content,'<canvas[^>]+id="glCanvas"','g')) as canvas, (select count(*) from regexp_matches(content,'id="(bgLetters|glyphs)"','g')) as glyph_host, (select count(*) from regexp_matches(content, '<body[^>]+data-fg-persist="(static|interactive)-v1"','g')) as page_contract, (select count(*) from regexp_matches(content,'<main[^>]+data-fg-page','g')) as payload_main, case when position('data-fg-page-style' in content)>0 then 1 else 0 end as page_style, (select count(*) from regexp_matches(content, 'data-fg-controller="/fg-page-[^"]+\.js"','g')) as controller, (select count(*) from regexp_matches(content, '@keyframes fgEnter\{from\{opacity:0\}to\{opacity:1\}\}','g')) as arrival_keyframe, case when position('.fg-progress-rule{' in content)>0 or position('.rule{position:absolute;left:0;right:0' in content)>0 then 1 else 0 end as local_progress_copy, (select count(*) from regexp_matches(content, 'FGModules\.load|fg-devnav\.js|id="fgFade"|F_PATHS|localStorage\.getItem\("fg:pal"\)','g')) as forbidden_local_copies from page;

Final browser check

Open the page directly, then reach it from another compatible interface page and leave it again. Check desktop and 390px mobile. The sticky header, WebGL canvas and glyph host must remain the same DOM objects; the atmosphere must not restart; there must be no flash, overflow, duplicate action or console error. If the page has a footer section rail, tap every chip: the active state must appear immediately, smooth scrolling must land on the correct section, the active chip must stay revealed in the horizontal rail, and no content may flash or leak over/through the footer during arrival or departure. Test Back and Forward too. Authenticated pages must retain their access boundary.

Editorial flipbooks are different

The six hand-built books deliberately keep full-document navigation because their bespoke flipbook, sound and atmosphere engines do not yet have lifecycle controllers. Their colour-matched entry and return transition is centralized separately. Do not use a book as the starting template for an interface page.
