00 · The claim under test

Can The Core Stay Still

Test 01 asked whether IDUI transfers away from the product it was written in. This asks the narrower, harder question: the core that Flipgazine corrected — meeting a radically different editorial product, can it mostly stay still?

Origarium is an archive with a reader inside it. Its chrome is near-black with an acid lime; its documents are warm paper. It sets long-form prose in a serif while its interface is a sans and its metadata a monospace. None of it was designed with IDUI in mind and almost none of it looks like Sindhorn.

Five predictions were frozen before the work. The one that mattered: the core exposes a single material family — app-glass.css, the --app-glass-* tokens, and the rule that a card is anything drawing an edge — and Origarium would need at least two. If that proved wrong, and one generalised material could express it, that would have been a real result too, published as one.

01 · The source, and the boundary

Read, Never Written

Cloudflare serves a nine-kilobyte shell; everything real is a row in a Supabase project this application shares with two others.

The rule

Origarium's rows belong to another application. The experiment may read and snapshot them and must never write to them. Reconstruction happens separately.

How that was enforced

Every Supabase request in the harness is intercepted; reads are answered from the frozen snapshot and writes aborted. The page carries a POST to a visit counter but does not fire it here, so each viewport makes a deliberate write attempt of its own and the run is invalid unless all three are refused. The guard is demonstrated every run rather than assumed.

What is committed

The snapshot with its version and md5, verified against the database so it is exact rather than approximately current, with the publishable key redacted. A live row can move; if the version leaves 59 the run is annotated, never silently carried forward.

03 · Two candidates

Valid Is Not Selected

The first reconstruction passed every contract and the owner rejected it. It is kept uncorrected, because deleting it would destroy the most useful thing this test has.

The original says the paper is the page: the warm material occupies the environment and the interface sits quietly on it. Candidate A said the paper is a surface inside the app — a dark shell, a rounded dark container, a cream document within. A different composition, not a styling difference.

It happened because the reader was built on the library's dialog, which is how that library puts a layer over a page — and which carries a scrim, a floating panel and chrome wrapping content. Reaching for it imported an assumption that had nothing to do with Origarium. That is the failure Test 03 predicts as identity convergence, arriving through a primitive rather than a value, and showing up in a real experiment before the test written to look for it.

What the rejection found

Material by role answers what is this surface made of. It does not answer how much of the world is it. An embedded preview and a full reader are the same material at different scope, and no token could have fixed Candidate A, because the difference is not what the material is — it is where it applies.

So the scene declares its context and the constitution derives the ground from it. A page says "this is a reading context"; it never says warm, or cream, or a hex value.

Both candidates carry zero page CSS, zero style attributes and zero appearance decisions. Contracts define validity; the editor selects quality. Only B was selected.

The one marked A

The core said it plainly: nothing recedes, scales or parallaxes — opacity or scale above a backdrop-filter makes the frost flash flat mid-move. That is true, it was measured, and it is not a law about motion. It is a law about glass.

Origarium's reader is opaque paper on a plain scrim with no blur anywhere in the moving subtree, and the original springs: rise, overshoot a little past rest, settle. The rule is not deleted, because it is correct where it applies. It now states its condition, and the condition is enforced rather than documented — give a glass constitution a spring and the build fails, naming the material that may not scale.

IDUI needed that last row not to grow, and it did not. But neither did Origarium's. A page that styles by class holds its exceptions up front rather than manufacturing them per instance, so a hundred content instances multiply no styling authority on either side.

Scale therefore does not show IDUI absorbing variation better. It shows both absorbing it completely, with the difference sitting exactly where the reconstruction found it — a difference of locality, not of robustness under volume.

06 · Hostile content

Both Failed, In Different Shapes

Twenty-two records neither architecture was designed to receive: a four-hundred-character title, an unbroken hash, a URL, Thai and Japanese, right-to-left Arabic, emoji, markup in a title, an empty body, a forty-thousand-character paragraph. Legitimate but unanticipated — never malformed, because malformed input tests a parser.

One unbroken token took Origarium's whole page — more than two phone screens of overflow — and once that happens no card sits inside the viewport, so the count is one failure taking every card with it rather than twenty-two separate ones. IDUI's grid held and its typography did not: five paragraphs overflowed while every sheet stayed the same shape.

The repair was the same size on both: one declaration. Anyone claiming IDUI made it smaller would be wrong. The difference is reach — in the core it is a rule that reached two other products for nothing, and in a page it reaches that page. The site has 45 HTML pages carrying their own style blocks, and nothing in that architecture says which of them style text.

Both escape correctly. Markup in a title is shown and never run on either side, which is worth stating because it is the one hostile case where failure would be a security defect rather than a layout one.

07 · Verdict

Structural Pass, Editorial Seventy

Presentation burden is evaluated only against a reconstruction the owner has accepted. Zero of it with rejected fidelity is not a win — it is unresolved. Both halves are required, and only one of them is complete.

Owner editorial assessment — subjective

Around 70% close to the original. Acceptable as a repeatable template — yes. But it does not totally match my original intent. The font in the thumbnail is still wrong. The black bezel is too wide. The styling of the full-screen e-ink is still wrong, and it is not really full-screen: it should hide the header.

Not repaired, because repairing them would invalidate the judgement that names this result. Any correction is a Candidate C with a verdict of its own.

08 · What measurement could not read

The Finding That Outranks The Numbers

Asked why the second candidate was better, the owner answered: because you got a brief of the inspiration.

Everything between A and B came from one sentence of design intent — the thumbnail is an e-ink reader, and pressing it bounces to full screen — and not from further measurement. The instruments had already read every value on that page: the colours, the type scale, the radii, the spring curve to three decimal places. They could not read what the thing was.

So a constitution written from rendered outcomes recovers values faithfully and recovers intent not at all. Candidate A was a correct reading of every measurement and the wrong object, and the gap was closed by a designer saying what he had meant.

This is inherited by the next test as a warning rather than a lesson learned. A reconstruction of a third-party product from measurement alone will reproduce its values and miss whatever it meant — and no amount of instrumentation will say which parts those are, because the designer will not be there to tell us.
