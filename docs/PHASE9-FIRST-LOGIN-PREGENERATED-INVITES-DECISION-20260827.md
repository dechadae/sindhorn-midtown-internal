# Phase 9 — First Login Pre-Generated Invite Decision

**Date:** 27 August 2026  
**Status:** Approved product decision

## Decision

The first employee login must not depend on HR, a manager workflow, or a hotel Microsoft 365 account.

The rollout operator supplies the Sindhorn Midtown employee roster. Employees are pre-provisioned in the Sindhorn employee directory before launch.

The normal first-login flow is:

```text
pre-provision Employee ID
→ generate a single-use 6-digit activation code
→ deliver the code to the employee through their personal email or SMS
→ employee opens Sindhorn Midtown Internal
→ Employee ID + one-time code
→ Supabase authenticated session
→ code is consumed and cannot be reused
→ employee remains signed in on the device
```

Microsoft 365 remains future-ready in the identity architecture but is not shown as a login option during the current rollout because the hotel does not currently have the required Entra tenant administration available to this project.

## Provisioning authority

The rollout operator / Sindhorn app administrator is the provisioning authority. HR integration is not required.

The operator may provide employee records in a batch. At minimum each record needs:

- Employee ID;
- display name;
- preferred language (`th` or `en`).

Optional operational fields include:

- department;
- app role;
- account type;
- personal email for invite delivery;
- personal mobile number for SMS invite delivery.

Personal email/mobile details are delivery data, not identity authority. The Employee ID record in `public.sindhorn_employees` remains the canonical employee identity. Personal contact details should not be copied into the long-lived public employee profile unless a later approved feature genuinely needs them.

## Code generation

Normal employee activation codes are generated by the trusted Auth Worker using `ACTIVATION_PEPPER`, stored only as keyed hashes, rate-limited, single-use, and revocable.

The plaintext code may be shown once to the authorized administrator so it can be sent to the employee. It must not be written into GitHub, UI-pack content, logs, or long-lived audit metadata.

The current implementation uses 6 numeric digits and the existing activation expiry/attempt-lock policy. Expired codes can be regenerated without changing the Employee ID record.

## Delivery

Initial rollout can use operator-controlled delivery:

- personal email;
- SMS;
- another direct private channel approved by hotel operations.

The application backend does not need to retain the personal delivery address after the invitation is sent. Automated email/SMS delivery can be added later behind a dedicated provider integration without changing the employee identity model.

## Recovery

Recovery uses the same Employee ID identity but a newly issued single-use code. A recovery code never changes employee role, department, or authorization.

## Security rules

- No shared hotel password.
- No permanent 6-digit PIN.
- Employee ID alone is never sufficient to authenticate.
- Activation codes are single-use.
- Online attempts remain rate-limited and lock after repeated failures.
- Admin role/authorization stays server enforced.
- Personal email/SMS delivery addresses are not authorization claims.
- Microsoft 365 can be enabled later as a second login method for a pre-provisioned employee without creating a duplicate employee profile.
